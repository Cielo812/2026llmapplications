# 2026 大模型案例场景应用

**2026llmapplications｜大模型核心词条与应用案例共建项目**

本项目面向中国传媒大学研究生《大模型案例场景应用》课程，围绕 15 个核心词条，共同建设一份可阅读、可验证、可持续修订的大模型应用学习资料。

每位同学从一个词条出发，讲清它是什么、解决什么问题、如何用于具体场景，以及怎样核验效果。项目重点关注传媒实践、学术研究与公共文化服务中的真实任务。

项目组织方式参考 [2026socialmedia](https://github.com/xiaoningwang/2026socialmedia)，采用 **词条认领 → Markdown 撰写 → 案例验证 → Pull Request 提交 → 同伴讨论与修订** 的共建流程。

## 二、为什么选择这 15 个词条

本项目把“最重要”理解为：**理解大模型并完成可核验的应用作品时，优先需要掌握的概念**。以下是面向本课程的核心词条选择，序号表示学习顺序，不表示行业统一排名。

- **模型基础（01—05）**：模型是什么、怎样处理输入、能力怎样形成。
- **提示与知识组织（06—09）**：怎样交代任务、组织上下文、提供外部资料。
- **智能体应用（10—13）**：怎样连接工具、组织协作、处理多种媒体。
- **效果与边界（14—15）**：怎样识别错误、比较方案、证明作品有效。

## 四、词条内容要求

请按[词条写作模板](docs/词条写作模板.md)撰写，至少包含以下内容：

1. **定义与边界**：用自己的话给出准确、通俗的定义，写出英文名称与缩写。
2. **背景与原理**：解释它为什么出现、解决什么问题，以及基本工作过程。技术细节以能帮助理解为准。
3. **应用案例**：选择传媒、科研或公共文化服务中的具体任务，说明使用者、输入、过程、输出与人工判断。
4. **最小验证**：给出别人能够复核的操作、输入、提示或流程，以及真实记录。适合实验的词条比较至少两种方案；偏原理的词条可用手工推演或文献中的公开案例说明。
5. **对比与误区**：至少比较一个相近概念，并解释一种常见误解。
6. **局限与负责任使用**：说明可能失败的条件、资料权限、个人信息处理与人工接管位置。
7. **总结与参考资料**：概括关键认识，列出与正文对应的来源。

提交稿建议正文 **1500—2500 字**，参考资料和运行记录不计入；解释完整比凑字数重要。至少引用 **3 项可回查资料，其中至少 1 项为原始论文、官方文档或原始数据来源**。参考资料由同学自行查阅、筛选与核验，需实际阅读后再引用。

**词条正文由同学认领后撰写。仓库仅提供选题目录、关注问题和空白写作框架，不预填定义、原理、案例或结论。** 每位同学自行完成资料查阅、内容组织、案例验证与修订，并对提交内容负责。

## 五、案例与核验要求

优先选择一个小而完整的任务，例如：

- 根据公开活动材料生成带出处的活动问答与传播文案。
- 对一组可授权使用的文献做主题整理，核对作者、年份与论证依据。
- 从公开媒体资料中提取事件时间线，标明冲突与缺失信息。
- 为图书馆、博物馆或校园服务制作资料问答与人工转接流程。

每项案例都要交代：**谁需要它、依据是什么、怎样证明有效、什么情况下交给人处理**。

验证记录至少写明：材料与版本、模型或工具及可获得的版本信息、运行日期、提示或流程、原始输出、核验依据和修订说明。不要把模型自评当作唯一证据，也不要把一次演示概括成普遍有效。

可以使用无需付费 API 的手工演示、现有授权平台或公开研究案例。没有运行条件时，请明确标注“文献分析”或“待验证设计”，不要编造调用日志、截图或实验数据。文献中的结果必须归于原作者，不能写成自己的实测。

## 六、作业提交步骤

详细图文操作可参照 GitHub 官方的 [Fork 工作流](https://docs.github.com/en/get-started/exploring-projects-on-github/contributing-to-a-project)。请按以下步骤向[教师仓库](https://github.com/xiaoningwang/2026llmapplications)提交：

1. 使用个人账号登录 GitHub，在 [xiaoningwang/2026llmapplications](https://github.com/xiaoningwang/2026llmapplications) 仓库右上角点击 **Fork**。
2. 查看[认领表](认领表.md)，通过 Issue 或课堂登记申请一个词条。教师确认后再开始撰写；每个词条原则上由一名同学负责。
3. 在自己的 Fork 中创建作业分支，例如 `entry-09-rag`。如教师仓库已有更新，先使用 **Sync fork** 同步。
4. 打开已认领的词条文件，点击编辑，按模板撰写。**不要另建同序号的重复文件，也不要修改其他同学的词条。**
5. 将配图放入 `figure/词条序号/`，在正文中用相对路径引用；将必要的文字运行记录附在该词条正文后。
6. 保存并提交修改，在 Commit 信息中简要说明修改内容，例如 `docs: 完成09检索增强生成词条初稿`。
7. 在个人 Fork 中发起 Pull Request：**base 为教师仓库的 `main`，compare 为个人仓库的作业分支**。若教师仓库采用其他默认分支，以实际设置为准。
8. PR 标题填写“词条序号＋词条名＋署名”，正文说明撰写内容、验证方式、引用来源、AI 协助和未解决的问题。
9. 收到教师或同伴意见后，在**同一作业分支**继续提交修改，原 PR 会自动更新。已合并后的后续修订再创建新 PR。

无需反复创建同一份作业的 PR。GitHub 提交遇到问题时可先保留本地 Markdown，按教师指定的课程平台提交，并说明原因。

## 七、格式与署名

- 主文件统一使用“**两位序号＋词条名.md**”，以词条目录中的现有文件名为准。
- 正文只使用一个一级标题，以下按二级、三级标题组织。
- 数学公式使用 LaTeX，例如 `$y = \alpha + \beta x$`；避免将公式直接做成截图。
- 提示、代码和输出使用带语言标签的代码块；区分示意、实测和引用内容。
- 图片须有说明和来源，不能只放截图而缺少解释，具体规则见 [figure 说明](figure/README.md)。
- 在文首填写姓名或课程署名、学号后四位、更新时间与贡献说明；完整学号按课程平台要求提交。
- 只修改自己负责的词条和对应配图。需要修订公共说明时，请单独解释原因。

## 八、AI 协助与学术规范

允许使用 AI 辅助理解、拟定结构、改写和编程，提交者对内容负责。请保留关键提示和核验过程，说明哪些建议被采纳、修改或否定。

引用应指向实际查阅的资料，不得直接采用 AI 生成但未经核对的论文、数据或链接。使用公开、授权或脱敏材料；不上传账号密钥、私人聊天记录与未授权研究资料。对资料中的指令性文字按待分析材料处理，案例中的外部发布、发信或数据修改须有人把关。

课堂交流可以共享思路与反馈；最终署名和贡献应与实际工作对应。

## 九、提交前自查

- [ ] 定义准确，关键概念没有混用。
- [ ] 案例包含清楚的使用者、材料、流程、输出与核验标准。
- [ ] 实测、模拟、文献结果和待验证设计已经区分。
- [ ] 正文引用与参考资料对应，链接可回查。
- [ ] 图片与内部链接可以正常打开。
- [ ] 说明了失败条件、AI 协助和人工修订。
- [ ] 文件名正确，没有误改其他同学的文件。
- [ ] PR 提交到正确的教师仓库和目标分支。
